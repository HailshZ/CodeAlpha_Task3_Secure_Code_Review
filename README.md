# Secure Code Review: Flask Application

A detailed secure-code-review project for **CodeAlpha Task 3**. It demonstrates how to identify security weaknesses in a Flask application, confirm them with a static application security testing (SAST) tool, remediate them, and verify that the corrected application behaves safely.

The repository intentionally includes two versions of the application:

- [app.py](app.py) — deliberately vulnerable and **not safe to deploy**.
- [app_fixed.py](app_fixed.py) — the reviewed and remediated version.

The project uses **manual static analysis** and **Bandit** to investigate security issues. It also explains how the application receives input, processes it, and sends output back to a browser or API client.

## 1. Project overview

This repository demonstrates a complete secure-code-review workflow:

1. **Manual review** identifies untrusted input and unsafe operations.
2. **Bandit** scans the source code and reports known dangerous patterns.
3. **Security findings** are mapped to CWE identifiers and OWASP categories.
4. **Remediation** replaces unsafe patterns with safer alternatives.
5. **Verification** compares the vulnerable and fixed applications.
6. **Documentation** explains the security principles and how each endpoint works.

The intended learning outcome is not simply “make the application run.” The goal is to understand **why each dangerous operation is unsafe and how a secure replacement protects the application**.

## 2. How the application works

The project is a small Flask web application. Flask maps URL paths to Python functions using route decorators. A browser or HTTP client sends a request to a route, Flask passes the request to the route function, and the function returns an HTTP response.

The application has two primary categories of functionality:

- **HTML output routes** receive request parameters and return rendered HTML.
- **Data-processing routes** receive encoded data and perform parsing or database operations.

The vulnerable application also contains a helper function that demonstrates SQL injection. This function is not currently exposed through an HTTP route, so it is mainly useful as a controlled code-review example.

### Application initialization

The application object is created with:

```python
app = Flask(__name__)
```

Flask uses this object to register routes and configure the development server. The application name is used by Flask to locate templates, static files, and application resources.

The vulnerable version starts with:

```python
app.run(debug=True, host='0.0.0.0', port=5000)
```

This means:

- `debug=True` enables Flask/Werkzeug debugging behavior.
- `host='0.0.0.0'` listens on every available network interface.
- `port=5000` uses port 5000.

The fixed version instead uses:

```python
app.run(debug=False, host="127.0.0.1", port=5000)
```

It disables debugging and binds only to the local machine.

## 3. The vulnerable application

The vulnerable source is intentionally unsafe. It is designed to show how a developer can trace an untrusted value from the request to a dangerous operation.

### 3.1 Hardcoded credentials

The vulnerable application defines:

```python
ADMIN_PASSWORD = "admin123"
```

This is a hardcoded password. It is stored directly in the source file and therefore becomes available to:

- Anyone who has access to the repository.
- Anyone who can read the source code.
- Anyone who can inspect the Git history.
- Anyone who receives a copied archive of the project.

A source-code password is not secret once it is committed. A real application should obtain a credential from an environment variable or a dedicated secret-management service:

```bash
export ADMIN_PASSWORD='a-strong-random-password'
```

The fixed version reads the value at runtime:

```python
ADMIN_PASSWORD = os.environ.get("ADMIN_PASSWORD")
```

This is better because the password can be changed without modifying the application source. However, the current project only demonstrates the secret-loading pattern. It does not implement authentication or use the password in a login flow.

> The environment variable is not a substitute for strong password generation, secure storage, rotation, and proper authentication. It is only a safer way to supply a password during deployment.

### 3.2 SQL injection

The vulnerable helper function is:

```python
def get_user(username):
    conn = sqlite3.connect('users.db')
    cursor = conn.cursor()
    query = "SELECT * FROM users WHERE username = '" + username + "'"
    cursor.execute(query)
    user = cursor.fetchone()
    conn.close()
    return user
```

The function builds a SQL statement by concatenating the `username` value.

For example, if the input is:

```text
admin' OR '1'='1
```

the generated query becomes:

```sql
SELECT * FROM users WHERE username = 'admin' OR '1'='1'
```

The injected `OR` condition changes the meaning of the query. Instead of returning only the matching user, the condition can return every row.

This is a **SQL injection vulnerability** because attacker-controlled data is being interpreted as part of the SQL statement rather than as data.

#### Why the fixed code uses a parameterized query

The fixed version uses:

```python
cursor.execute(
    "SELECT * FROM users WHERE username = ?",
    (username,),
)
```

The SQL statement contains a placeholder, and the username is passed separately as a parameter. SQLite treats the username as data, so the attacker cannot change the query structure.

The fixed version is safer because:

- The query text remains constant.
- The database driver handles parameter binding.
- A malicious value cannot introduce another SQL clause.
- The same code works with values containing quotes, apostrophes, or SQL keywords.

The helper is not currently exposed through an HTTP route, and no `users.db` file is created by this repository. This limits the demonstration to source-level review rather than a live database attack.

### 3.3 Reflected cross-site scripting

The vulnerable `/greet` route is:

```python
@app.route('/greet')
def greet():
    name = request.args.get('name', 'Guest')
    return f"<h1>Hello, {name}</h1>"
```

The route reads the `name` query parameter through Flask’s `request.args` object:

```python
request.args.get('name', 'Guest')
```

If the browser requests:

```text
/greet?name=<script>alert(1)</script>
```

the application returns HTML containing the script tag. A browser can interpret that content as executable JavaScript rather than plain text.

This is **reflected cross-site scripting**, or XSS. The attacker-controlled value is reflected into the response without escaping.

#### How the fixed version protects the output

The fixed version uses MarkupSafe’s `escape()` function:

```python
from markupsafe import escape

return f"<h1>Hello, {escape(name)}</h1>"
```

For input such as:

```text
<script>alert(1)</script>
```

The output becomes:

```html
<h1>Hello, &lt;script&gt;alert(1)&lt;/script&gt;</h1>
```

HTML entities are displayed as text rather than interpreted as markup. Therefore, the browser does not execute the supplied script.

The escape step is important because the application has no separate template engine. It directly constructs HTML and must protect that output before returning it.

#### Why Bandit does not report XSS

Bandit is a pattern-based SAST tool. It does not always understand server-side context such as the relationship between a request parameter and an HTML response. Therefore, the original application’s XSS is visible during manual review but may not appear in a Bandit finding list.

Manual review remains necessary because static analysis cannot identify every context-dependent vulnerability.

### 3.4 Insecure deserialization

The vulnerable `/load` route reads a Base64-encoded value:

```python
data = request.args.get('data')
if data:
    decoded = base64.b64decode(data)
    obj = pickle.loads(decoded)
```

`pickle` is an object serialization format. Unlike JSON, pickle can contain instructions that cause Python to invoke functions while loading an object. A malicious pickle can therefore execute code in the server process.

This is called **insecure deserialization** and is commonly associated with CWE-502.

Example data flow:

```text
HTTP request parameter data
        ↓
base64.b64decode(data)
        ↓
unsafe pickle.loads(decoded)
        ↓
python object or arbitrary code execution
```

A pickle payload can execute code before the application receives a normal Python object. The risk is especially serious because the input can come from an HTTP request.

#### Secure replacement behavior

The fixed version does not use pickle. Instead, it expects Base64-encoded JSON:

```python
obj = json.loads(base64.b64decode(data, validate=True))
```

The sequence is:

```text
HTTP request parameter data
        ↓
Base64 decoding with strict validation
        ↓
JSON parsing
        ↓
Python list, dictionary, string, number, or boolean
        ↓
HTML escaping before response
```

JSON can represent ordinary data, but it cannot directly encode executable Python behavior. This makes it suitable for untrusted input.

The fixed route catches malformed values and returns HTTP `400`:

```python
except (binascii.Error, ValueError):
    return "Error loading data", 400
```

This provides a clear failure response instead of allowing an exception to become a server error.

### 3.5 Debug mode and network binding

The vulnerable startup configuration is:

```python
app.run(debug=True, host='0.0.0.0', port=5000)
```

Two configuration problems occur together:

1. **Debug mode** can expose Werkzeug’s interactive debugger and detailed tracebacks.
2. **All-interface binding** makes the server visible to other systems on the network.

A debug server may expose internal source paths, environment variables, request data, and potentially an interactive execution console. This is a high-risk configuration for a public or shared network.

The fixed configuration is:

```python
app.run(debug=False, host="127.0.0.1", port=5000)
```

- `debug=False` disables the debugger.
- `127.0.0.1` allows only local connections.
- The application can still be tested locally through curl or a browser.

## 4. Remediated application

[app_fixed.py](app_fixed.py) contains the reviewed and corrected implementation.

### 4.1 Secret loading

The application reads the password from the environment:

```python
ADMIN_PASSWORD = os.environ.get("ADMIN_PASSWORD")
```

The environment value is not included in the source file. The developer can supply the value when starting the application:

```bash
export ADMIN_PASSWORD='replace-with-a-strong-value'
flask --app app_fixed run --host 127.0.0.1 --port 5001
```

The fixed source does not perform authentication. The value represents a Placeholder secret for review and can be expanded in a future authentication implementation.

### 4.2 Parameterized database access

The fixed `get_user()` function is:

```python
def get_user(username):
    conn = sqlite3.connect("users.db")
    try:
        cursor = conn.cursor()
        cursor.execute(
            "SELECT * FROM users WHERE username = ?",
            (username,),
        )
        return cursor.fetchone()
    finally:
        conn.close()
```

The `try/finally` block ensures that the database connection is closed even if the query fails or returns an error.

### 4.3 Escaped HTML output

The `/greet` route is:

```python
@app.route("/greet")
def greet():
    name = request.args.get("name", "Guest")
    return f"<h1>Hello, {escape(name)}</h1>"
```

The process is:

1. Flask reads the `name` query parameter.
2. The value is passed to `escape()`.
3. Unsafe HTML characters are converted to entities.
4. The result is inserted into the HTML response.

### 4.4 Safe data loading

The fixed `/load` route performs the following steps:

1. Reads the `data` request parameter.
2. Returns `No data` when the parameter is missing.
3. Decodes Base64 with strict validation.
4. Parses the decoded content as JSON.
5. Escapes the resulting value before returning it as HTML.
6. Returns HTTP `400` for invalid Base64 or invalid JSON.

This is a deliberately intentionally simplified safe data format. It is not a production data-storage layer, but it demonstrates how to avoid code execution from user-provided data.

### 4.5 Local-only server

The fixed application binds only to the local machine:

```python
app.run(debug=False, host="127.0.0.1", port=5000)
```

This prevents the application from being directly reachable from another computer on the network during local testing.

## 5. Bandit findings and what each test means

Bandit scans Python source code and looks for known insecure patterns. It does not guarantee that an application is secure; it only identifies patterns that its configured rules recognize.

| Test ID | Finding | Severity | Meaning | Remediation |
|---|---|---|---|---|
| B403 | Import of `pickle` | Low | The module can be dangerous when deserializing untrusted data. | Remove pickle-based deserialization. |
| B105 | Hardcoded password | Low | A password string appears in source code. | Read a secret from an environment variable or secret manager. |
| B608 | SQL injection construction | Medium | SQL is built by string concatenation. | Use parameterized queries. |
| B301 | Unsafe `pickle.loads` | Medium | Untrusted data may result in arbitrary code execution. | Use JSON or another safe data format. |
| B201 | Flask debug mode | High | Debug mode can expose an interactive debugger. | Disable debug mode. |
| B104 | Binding to all interfaces | Medium | The server may be reachable from the network. | Bind only to `127.0.0.1` during local development. |

The following explanation applies to each finding:

### B403: pickle import

Bandit flags importing the pickle module because pickle can represent executable behavior. The import itself is not always dangerous; the dangerous operation is using pickle to deserialize untrusted data.

### B105: hardcoded password

Bandit reports the literal value `admin123` as a possible password. The string may be a demonstration credential, but the scanner cannot know whether it is a real credential or a test value. Treating it as a real secret is unsafe.

### B608: SQL query construction

Bandit identifies a string-based SQL query that includes an untrusted value. The `get_user()` function directly concatenates `username` into the statement.

### B301: unsafe pickle deserialization

Bandit flags `pickle.loads()` because pickle data can invoke Python methods while being loaded. The vulnerable route accepts the serialized data through `request.args`.

### B201: Flask debug mode

Bandit flags `debug=True` because it may expose the Werkzeug debugger. The route and stack-trace information can become visible during development.

### B104: all-interface binding

Bandit flags `host='0.0.0.0'` because the server is made accessible to every network interface. This can allow unintended remote access.

## 6. How to run the project

### 6.1 Install dependencies

Create and activate a virtual environment:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

On Windows PowerShell, activate the environment with:

```powershell
venv\Scripts\Activate.ps1
```

The project dependencies are:

```text
flask
bandit
```

The `requirements.txt` file contains the package names required by the project. The repository’s local virtual environment is already available in the workspace, but a fresh installation is recommended when copying the project elsewhere.

### 6.2 Run the vulnerable application

For a local, non-public demonstration:

```bash
flask --app app run --host 127.0.0.1 --port 5000
```

The command tells Flask to load the `app` object from [app.py](app.py). The route definitions are registered automatically.

The vulnerable app is intentionally unsafe. Do not use it with a public hostname or expose it through a reverse proxy.

### 6.3 Run the fixed application

```bash
flask --app app_fixed run --host 127.0.0.1 --port 5001
```

The fixed application uses the same generally named routes but contains sanitized input handling and safe data parsing.

### 6.4 Run Bandit

Scan the vulnerable source:

```bash
bandit -r app.py
```

Scan the fixed source:

```bash
bandit -r app_fixed.py
```

Generate the HTML report:

```bash
bandit -r app.py -f html -o bandit_report.html
```

The report is stored in [bandit_report.html](bandit_report.html).

### 7.1 Greeting route

Vulnerable URL:

```text
http://127.0.0.1:5000/greet?name=Hailem
```

The response is:

```html
<h1>Hello, Hailem</h1>
```

Malicious input:

```text
http://127.0.0.1:5000/greet?name=<script>alert(1)</script>
```

Vulnerable behavior:

```html
<h1>Hello, <script>alert(1)</script></h1>
```

The browser sees an executable script element.

Fixed behavior:

```text
http://127.0.0.1:5001/greet?name=<script>alert(1)</script>
```

The response is:

```html
<h1>Hello, &lt;script&gt;alert(1)&lt;/script&gt;</h1>
```

The browser displays the input as text.

### 7.2 Data-loading route

The fixed application accepts a Base64-encoded JSON value.

Create valid Base64 data:

```bash
echo -n '{"user":"hazel"}' | base64
```

Send it to the fixed application:

```bash
curl -G --data-urlencode "data=$(echo -n '{"user":"hazel"}' | base64)" \
  http://127.0.0.1:5001/load
```

Expected response:

```text
Loaded: {'user': 'hazel'}
```

Invalid data:

```bash
curl -i -G --data-urlencode "data=not-valid" \
  http://127.0.0.1:5001/load
```

The application returns HTTP `400` because the value is not valid Base64-encoded JSON.

### 7.3 Database helper example

The SQL injection helper is not part of the HTTP interface. Its data flow is:

```text
username argument
        ↓
string concatenation
        ↓
SQL statement
        ↓
sqlite3 cursor execution
```

In the fixed version, the data flow is:

```text
username argument
        ↓
parameter tuple
        ↓
SQLite parameter binding
        ↓
query result
```

The fixed version cannot interpret the username as SQL syntax.

## 8. Security concepts explained

### 8.1 Untrusted input

Untrusted input is data supplied by a user, browser, API client, or another remote system. Examples include:

- Query parameters.
- Form fields.
- HTTP headers.
- JSON request bodies.
- Database values.
- Environment variables.
- File contents.

The application must treat every externally supplied value as potentially malicious unless it has been validated and safely processed.

### 8.2 Injection

Injection occurs when untrusted input changes the structure of an interpreter or query language. Examples include:

- SQL injection.
- Command injection.
- HTML injection.
- Code injection.

The safe solution is to avoid building executable statements from user input. Use parameterized queries, allowlists, strict validation, and output encoding.

### 8.3 Cross-site scripting

XSS occurs when untrusted input is inserted into HTML without proper encoding. The browser interprets the input as markup rather than text.

The correct defense is:

- Escape output in HTML contexts.
- Use a template engine with automatic escaping.
- Avoid constructing HTML with string concatenation when user input is present.

### 8.4 Deserialization

Deserialization converts a serialized representation into Python objects. The following formats are dangerous when their input is untrusted:

- Pickle.
- Some object serializers.
- Formats that can represent executable behavior.

JSON is safer for ordinary data because it is designed to represent values such as strings, numbers, arrays, and objects rather than code execution instructions.

### 8.5 Hardcoded secrets

A hardcoded secret appears in source code and repository history. Secrets should be provided at runtime through:

- Environment variables.
- A secret-management service.
- A secure configuration store.
- A protected deployment system.

The secret should never be committed to Git.

### 8.6 Debug configuration

A development debugger can help developers diagnose errors, but it may expose interactive capabilities. Debug mode should be disabled in production and should not be exposed to untrusted users.

## 9. Why the project is structured this way

The repository separates the vulnerable and fixed implementations to make the comparison visible.

For example, a reviewer can compare:

```text
app.py:    query = "SELECT ... '" + username + "'"
app_fixed: cursor.execute("SELECT ... ?", (username,))
```

The comparison makes the security weakness and remediation easy to understand.

The report provides the scanner’s result, while the source code provides the technical detail. The documentation explains both the attack and the protective design.

This structure is useful for:

- Code review assignments.
- Security training.
- Classroom demonstrations.
- A final submission that contains both evidence and remediation.

## 10. Scope and limitations

This project demonstrates common code-level vulnerabilities, but it is not a complete production security review.

The application does not currently implement:

- User authentication.
- Authorization.
- Session management.
- CSRF protection.
- Secure HTTP headers.
- Database access controls.
- Rate limiting.
- Input length validation.
- Dependency vulnerability scanning.
- Dynamic application testing.
- Production logging and monitoring.

A production application would require additional review. Tools such as OWASP ZAP, Burp Suite, dependency scanners, and continuous integration security checks can extend the analysis.

The `get_user()` function is only an example. It is not currently connected to a route, and no database is created in this repository.

The `ADMIN_PASSWORD` value is only a placeholder. The project does not implement a real login flow.

## 13. Security checklist

Use this checklist when reviewing a similar application:

- [ ] Is every external input treated as untrusted?
- [ ] Are database queries parameterized?
- [ ] Are HTML values escaped before rendering?
- [ ] Is no unsafe deserialization used for request data?
- [ ] Do secrets come from environment variables or a secret manager?
- [ ] Is debug mode disabled outside local development?
- [ ] Is the application bound to localhost during development?
- [ ] Are invalid inputs rejected with safe HTTP responses?
- [ ] Are database connections closed after use?
- [ ] Are dependencies checked for known vulnerabilities?
- [ ] Is the application covered by automated tests and static analysis?
